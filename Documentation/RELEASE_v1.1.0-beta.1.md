## Updater channel contract

No updater code change — the existing logic already enforces the requirement.
`UpdateChecker`: a prerelease manifest is ignored unless the user's
`UpdateChannel` is `.prerelease` (default is `.stable`, opt-in only).

Tests (`UpdateCheckerTests`):
- `stableUserIsNotOfferedTheOneOneZeroBeta` — stable 1.0.0 user + manifest
  `1.1.0-beta.1` → `.upToDate` (stable → beta ignored).
- `betaChannelSeesTheBetaAndFinalSupersedesIt` — opt-in channel sees the beta;
  a beta user is later pulled to the `1.1.0` final on the stable channel.
- Pre-existing: `stableChannelIgnoresPrereleases`, `prereleaseChannelAcceptsPrereleases`,
  `offersNewerStable`, `equalVersionIsUpToDate`, `olderRemoteVersionNeverPrompts`.

## Artifact policy (locked)

| Artifact | Class | Beta.1 treatment |
|---|---|---|
| `CoreTend-1.1.0-beta.1-arm64.dmg` | **USER PRODUCT** — the download | The one obvious button on the site once published |
| `CoreTend-1.1.0-beta.1-arm64.zip` | machine/product convenience | Keep as the GitHub release's alternate asset (release scripts and some workflows expect it). **Do not** feature it in the site download funnel |
| `latest.json` | MACHINE-CONSUMED — in-app `UpdateChecker` reads it | Publish beside the assets. Never presented as a user download |
| `SHA256SUMS` | MACHINE / release-integrity — CI, gates, evidence | Publish. **No checksum tutorial in the main download path** |
| Minisign `.minisig` / `minisign.pub` | not consumed by the native updater | **Do not promote for the beta.** Defer to a later stable release unless the maintainer wants them |
| provenance fields in generated `latest.json` (`sourceCommit`, `releaseTag`, `treeState`, `buildInvocationID`) | INTERNAL / audit | keep, generated by `build-release.sh` |
| SBOM / SLSA attestation | INTERNAL / supply-chain | produced by the external signing runner; absent locally |
| `AUDIT_PACKAGE_SHA256SUMS` (`build-audit-package.sh`) | INTERNAL — tamper-detection for the audit ZIP | keep |

No internal verification step is removed or weakened. No release-security
script is deleted.

## Human steps to publish (in order — none done)

1. Complete the release-blocking human QA in `Documentation/BETA_QA.md`
   ("HUMAN VERIFICATION REQUIRED" list) and record each result with a date +
   build. **READY TO SIGN is NO until this is done.**
2. Register the App Group in the Apple Developer portal (above).
3. Reboot if `spctl`/`trustd` is wedged for Developer ID chains (a known
   local hazard after heavy `codesign` load — see `RELEASE_STATE.md`).
4. `Scripts/package-local.sh` → `Scripts/sign-and-notarize.sh 1.1.0-beta.1 CoreTend-Notary`.
5. `git tag -a v1.1.0-beta.1` at the reviewed commit →
   `CORETEND_RELEASE_SIGNED=1 Scripts/build-release.sh 1.1.0-beta.1`.
6. `bash Scripts/final-launch-gate.sh --expect-version 1.1.0-beta.1 --expect-head <sha>`
   → must be READY in the signed posture.
7. Minisign-sign `SHA256SUMS` (human — key password) *if* the maintainer wants
   Minisign for the beta; otherwise skip per the artifact policy.
8. `git push` branch + tag; `gh release create v1.1.0-beta.1 --prerelease
   --notes-file Release/Notes/1.1.0-beta.1.en.md <DMG> <ZIP> <latest.json>
   <SHA256SUMS>`.
9. `Scripts/sync-published-release.sh`; commit `Configuration/published-release.json`.
10. Website beta-channel sync (separate phase — see below). Do **not** deploy
    the site as part of this pass.
