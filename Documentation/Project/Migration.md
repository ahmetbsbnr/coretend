# Migration boundary

The app never discovers legacy data by scanning a real user home. Import starts only after the user selects an already created copy in Settings and confirms its preview. Two contracts are recognized:

- `coretend-preferences-v1.json`: JSON v1 fields `version`, `excludedPaths`, optional `language`; unknown keys, wrong types, unsupported languages and files over 1,000,000 bytes are rejected.
- A standalone `.sqlite` copy of the published 1.x store: contiguous `schema_migrations` versions 1–4, ordinary `exclusions` and `settings` tables with the published columns. Only `exclusions.path` is imported. Activity, security settings, favorites and recents are excluded. The 1.x language is stored separately in UserDefaults and is not read or imported from SQLite. The contract comes from the maintained 1.x `Sources/Persistence/Store.swift` and `Sources/CoreTendApp/L10n.swift`, not from a real user store.

Both readers reject symlink sources, unstable reads, non-regular files, unsafe paths (including NUL), and more than 1,000 exclusions. SQLite copies are capped at 64 MiB; adjacent WAL/journal files cause refusal. The selected file is read through a read-only descriptor, never opened by SQLite. SQLite validates a private immutable snapshot in a newly created 0700 temporary directory, which is removed after connection closure. The safety audit exempts only this exact cleanup immediately following private-directory creation; arbitrary runtime removal remains forbidden.

A copy must be a consistent standalone backup created while 1.x is stopped or with SQLite backup tooling. Merely omitting an active WAL can produce an apparently valid but stale/incomplete copy; the importer cannot prove its provenance. No automatic discovery, original-store copy or checkpoint is performed.

Import replaces Next exclusions only after preview/confirmation and records the content digest inside the same transaction as preferences and activity. SQLite leaves the current Next language unchanged; JSON can import its allowlisted language. Synthetic JSON and SQLite fixtures reject the final marker insertion after prior writes: all writes roll back, source bytes remain unchanged, and retrying the same preview succeeds exactly once. SQLite fixtures also check source mtime/permissions and absence of source sidecars, known versions, corrupt/unknown histories and unsafe paths. No real 1.x copy has been supplied or qualified as of 28 September 2026; this remains the manual P4.6 evidence requirement.


`SQLiteStore` owns schema versions in `PRAGMA user_version`. Schema v3 contains activity events, preferences, the legacy import ledger, and performance samples. Schema v4 adds a local `saved_files` table and recency index: favorites are explicit, recent history is opt-in and off by default, unknown sizes remain null, and only 100 non-favorites are retained. App writers include activity recording, Settings preference/import writes, performance history, and Explore recents/favorites. App readers include those views and the saved-file view; the CLI opens the store read-only for activity access. `LocalStoreAccess` opens the app store at its reconstruction-specific location, while migration tests inject unique temporary SQLite paths. No existing v3 row is rewritten by the v4 step.

`migrate()` applies any missing v1–v5 stages in one immediate transaction and writes version 5 only after the new table, index, and nullable failure-code column are created. On any error it rolls back the transaction and rethrows. A synthetic v3 fixture precreates `saved_files_recency` on a separate fixture table. Migration creates `saved_files`, then index creation fails on the name collision. The fixture verifies that rollback removes the new table, leaves version 3 and its event, language preference, and performance sample intact, and preserves the preexisting index and its table row. The test removes only the synthetic colliding index, retries on the same store, and verifies version 5, preserved v3 rows, an empty new saved-file table, and the recency index on that table. A separate fixture proves that an incomplete preexisting `saved_files` table is rejected at table creation rather than adopted as v4. The normal synthetic v1/v2/v3 fixtures also cover forward migration and repeat invocation.

When multiple app views open the same fresh store at launch, each connection can observe schema version 0 before waiting for SQLite's write lock. After acquiring `BEGIN IMMEDIATE`, `migrate()` re-reads `user_version` and applies only stages still missing. A two-connection fixture holds that lock until both migration tasks wait, then releases it and verifies both stores can use the resulting v5 schema. This prevents the losing connection from replaying stale DDL after another connection commits.

The same synthetic v3 fixture is backed up through SQLite's Online Backup API to a new temporary file, checked with `PRAGMA integrity_check`, and restored to a separate new temporary file. The test checks schema version and representative event, preference, and performance rows after restore. A corrupt source fixture is rejected and no destination is installed. These tests exercise fixture backup/recovery before compatibility migration; they do not touch or qualify any real user store.

For a manual local recovery, quit CoreTend first. Copy `~/Library/Application Support/CoreTend-Reconstruction/records.sqlite` to a private backup location. To restore, quit CoreTend, preserve the current database as a separate rollback copy, then copy the chosen backup into that database path and relaunch. If startup or migration fails, quit and restore the preserved current copy. Keep copies private and remove them when no longer needed. The app has no backup-management UI; SQLite fixture proof does not qualify this manual macOS procedure or real-store recovery.

Schema v5 adds nullable `activity_events.failure_code` inside the same immediate migration transaction. A v4 store receives one `ALTER TABLE`; fresh and older stores create prior schema stages then add the column before writing `user_version = 5`. Existing event rows retain SQL `NULL`; no reason is inferred from detail. A failed migration rolls back the column and version together, and retry uses the same version gate. The read-only CLI can still read v4 activity rows with null in-memory failure codes. Older v4 app binaries cannot open a v5 store because their schema gate rejects future versions; rollback requires a pre-upgrade backup or restoring the v5-capable binary. Activity JSON/CSV exports retain the original four fields.
