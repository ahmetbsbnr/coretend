# Restore / Undo a Cleanup

CoreTend's cleanup and Smart Care actions delete files by moving them
to the macOS **Trash** by default — not by permanent deletion — precisely so
mistakes are recoverable.

## Restoring files removed by Cleanup / Smart Care

1. Open **Finder → Trash**.
2. Find the item(s) — macOS preserves the original name; if you need to
   confirm origin, check CoreTend's Activity/History view for the scan
   summary (path, size, and date) recorded at cleanup time.
3. Right-click → **Put Back**, or drag the item back to its original
   location.

As long as you have not emptied the Trash, the removal is fully reversible.
Emptying the Trash (from Finder, or via "Empty Trash" automation) is a
macOS-level action outside CoreTend's control and is final.

## Restoring items flagged by Protection

Malware-scan findings use a separate mechanism — the app-owned Quarantine
folder, not the Trash. See [QUARANTINE.md](QUARANTINE.md) for how to
restore those.

## Dry-run mode

Every scan/clean flow (Cleanup, Smart Care, Protection) supports a
**dry-run** mode: the scan runs and shows exactly what would be removed and
how much space it would free, but nothing is deleted. Review the dry-run
results before running for real. Activity history records whether an entry
was a dry run (`dryRun` field in `~/Library/Application
Support/CoreTend/store.sqlite`).

## What Quarantine restore actually does (from the code)

This section is generated by reading `Quarantine.restore(_:)` in
`Sources/MalwareEngine/MalwareEngine.swift` and its caller in
`Sources/CoreTendApp/ProtectionView.swift` — it only claims what the code
genuinely does today.

- **Mechanism**: one `FileManager.moveItem(at:to:)` call per item, from the
  app-owned quarantine folder back to the exact `originalPath` recorded in
  the manifest at quarantine time. There is no Trash involved in this path.
- **Manifest-backed**: yes — `originalPath` is stored per item in
  `manifest.json` inside the quarantine directory, so restore always targets
  the real original location, not a guess.
- **Collision handling**: **none.** If a file already exists at
  `originalPath` (e.g. you saved a new file there after quarantining the
  old one), `moveItem` throws and the restore fails outright — the
  quarantined copy is left in place, nothing is overwritten. There is no
  rename-on-conflict or merge behavior.
- **Missing parent directory**: **not recreated.** If the original parent
  folder was deleted after quarantining, `moveItem` throws and restore
  fails; the file stays quarantined. You must recreate the folder yourself
  and retry (there is currently no retry-with-new-path UI — this is a real
  limitation, not a hidden feature).
- **Missing volume** (e.g. an external drive that's now unmounted): the
  move throws immediately (no such path); restore fails, item stays
  quarantined. No queuing or "restore when reconnected" behavior exists.
- **Permission denied**: if CoreTend can't write to the destination
  (e.g. a restricted system location), the move throws and restore fails
  the same way — quarantined copy untouched, no partial write.
- **Partial restores**: each item is restored individually, one
  `Quarantine.restore` call per user action. There is no bulk/"restore all"
  operation in the current UI, so there is no multi-item transaction to
  partially fail — a failure only ever affects the single item being
  restored.
- **File integrity**: the quarantined copy has its POSIX permissions
  reduced to `0o400` (read-only, no execute) while quarantined; on
  successful restore they're reset to `0o644`. The file's contents are
  never modified, only moved.
- **Activity/diagnostics logging — asymmetric today**: a **successful**
  restore is recorded to Activity history as a `.restore` entry (visible in
  My Activity and counted in the diagnostic report's activity counters, see
  [Settings → Data → Export diagnostic report]). A **failed** restore is
  **only** shown as a transient UI status message
  (`protection.restore_failed`) — it is *not* written to Activity history
  and does not increment the diagnostic report's error counters, because no
  `.error` activity record is created on this path. This is a known,
  honest gap: failed restores are not currently durably logged anywhere.

## Cleanup/Smart Care restore — no separate manifest

Unlike Quarantine, Cleanup and Smart Care removals have **no app-level
restore manifest of their own** — the only record kept is the Activity
history summary (counts, size, timestamp, dry-run flag), not a per-file
path list. Recoverability for these removals depends entirely on the
macOS Trash (see above), not on any CoreTend restore code. Do not
assume CoreTend can programmatically restore an individual cleaned
file by name — it cannot; only Finder's Trash "Put Back" can.

## If something looks wrong after a cleanup

1. Check the Trash first — most removed files are still there.
2. Check Protection → Quarantine if the item relates to a malware finding.
3. See [TROUBLESHOOTING.md](TROUBLESHOOTING.md).
4. If you believe CoreTend removed something it should not have,
   report it per [SECURITY.md](../SECURITY.md) or open a bug report (see
   `.github/ISSUE_TEMPLATE/`).
