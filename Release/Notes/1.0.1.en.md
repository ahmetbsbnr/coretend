# CoreTend 1.0.1

A single-defect patch release. **1.0.0 does not open.** If you downloaded it,
replace it with this build; nothing else about the app has changed.

## The app could not be opened

CoreTend 1.0.0 quit immediately at launch on every Mac except the one that
built it. There was no window, no error dialog and no Gatekeeper prompt — the
process trapped before the first frame:

    resource_bundle_accessor.swift:12: Fatal error: could not load resource
    bundle: from <app>/CoreTend_CoreTendApp.bundle or
    /tmp/coretend-release-build/arm64-apple-macosx/release/CoreTend_CoreTendApp.bundle

SwiftPM's generated `Bundle.module` accessor resolves the localization bundle
from exactly two locations: the `.app` root, and the absolute build directory
of the machine that compiled the binary. CoreTend ships that bundle in
`Contents/Resources`, which is the correct macOS layout and the only one
`codesign` accepts — content at an `.app` root is rejected outright. Neither
location the accessor checks was ever the one the bundle was in, so the only
branch that resolved was the build machine's own directory.

CoreTend now resolves the bundle from `Contents/Resources` directly.

## This was never a signing problem

1.0.0 was correctly Developer ID signed (Team NSCUV5G738), Apple-notarized and
stapled, and it still would not open. If a first launch was blocked or the app
appeared "damaged", that was this defect, not Gatekeeper and not a corrupted
download. Verifying the SHA-256 would not have revealed it. The signing,
notarization and stapling of 1.0.1 are unchanged from 1.0.0.

## Why the release gates did not catch it

Every release check CoreTend ran examined metadata — signature, notarization
ticket, staple, checksums, manifest fields. All of them passed for 1.0.0.
Nothing ever started the binary.

`Scripts/test-app-launch.sh` now does, on every build, in CI and in the release
pipeline. It launches the packaged app from a copy outside the build tree with
the build directory hidden, so a stale build directory cannot mask the failure
the way it masked this one. Run against the published 1.0.0 app, it fails.

## Also fixed

The published `.zip` asset carried an app with no stapled notarization ticket,
because it was packaged from the notarization submission copy rather than
rebuilt after stapling. That app opened only on a Mac able to reach Apple's
notarization service, and reported "damaged" offline or behind a proxy blocking
the ticket lookup. The `.dmg` was unaffected. Both artifacts are now verified
for signature *and* staple before publication.

## Unchanged

macOS 14.0 or later, Apple silicon (arm64). No telemetry, no account, no ads,
no device identifier. Scans stay on the Mac. Apache-2.0.
